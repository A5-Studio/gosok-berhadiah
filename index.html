The engine can't overspend

Pure random odds would let a busy first week drain the big tiers and leave late buyers with Rp 5K cards. Two rules stop that.

Weight by what's left. As a tier runs low its odds drop on their own, so the month ends close to the planned mix with no manual tuning.

Daily quotas. Each tier's stock is split across the scratch days. When every tier is capped, the card becomes a draw entry, so nobody loses.

Engineering decisions

The calls that kept it safe

GET-only API

instead of POST for writes

Apps Script answers a cross-origin POST with a 302 that drops the body. Designing around it early avoided a launch-day bug.

Prize decided before the scratch

instead of deciding on reveal

The server is the only source of truth. Closing the tab mid-scratch loses nothing, and the canvas can't be tampered with.

Locked, idempotent redeem

instead of dedupe by card only

Every write takes a script lock. A retried or double-tapped scratch returns the same prize instead of an error or a second prize.

Raw orders stay read-only

instead of flag columns on the export

Campaign state lives in its own tabs keyed by order ID, so the upstream export can refresh freely. Cancelled orders void unscratched cards.

Human check before money moves

instead of a direct balance API

A Thursday job builds one CSV row per merchant. Finance pays Friday, marks the batch DONE, and the system backfills every row.

Test mode inside production

instead of a staging stack

Eight reserved phone numbers run the real deployed API with fixed outcomes and never touch prize inventory.

Limits I chose

What I'd change at 10× volume

At 14,000 cards the spreadsheet was the right tool. Above about 50 concurrent scratches the global lock starts returning "system busy". Past that point I'd move to:
